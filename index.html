01

Goals and scope

Goals

  • The stamped text on the bar (1 gram, 24kt, 999) and the hallmark stay readable at every size.
  • Each device downloads only the pixels it can show.
  • Uploads go straight to storage; the API never streams image bytes.
  • Heavy processing runs once per upload, off the request path.
  • A placeholder paints instantly, so product grids never show empty tiles.
  • Replacing a photo never needs a cache purge.

Out of scope for this design

  • Video, 360° spins and AR views of the bar.
  • Background removal or retouching (done in the studio before upload).
  • Live gold price overlays on images (rendered by the app as text).
  • Marketing banners and email images, which can reuse the same pipeline later.

03

Upload path

Example: the studio exports gold-bar-1g-front.jpg, 4000 × 4000 px, about 8 MB. These steps match the numbers on the diagram.

  1. 1
    Admin → API

    The product form gets an id first (GET /products/new-id), then asks POST /uploads/signed-url with folder: products, the product id, purpose: primary, contentType: image/jpeg and contentLength: 8388608. The API returns a PUT URL valid for 300 seconds, with type and size signed into it.

  2. 2
    Admin → R2

    The browser PUTs the 8 MB file straight to the private uploads bucket. R2 rejects it if the type or size differs from what was signed.

  3. 3
    Admin → API

    The product is saved with images: [{ uploadKey, role: "primary", alt }]. The API creates a Media row as PROCESSING and saves the product at once, without waiting.

  4. 4
    API → Queue

    A process-image job is queued with the media id as its job id, so a double save can't queue it twice.

  5. 5
    Queue → Worker

    A worker picks up the job (2 at a time per worker process by default).

  6. 6
    Worker ↔ R2 uploads

    The worker downloads the raw file, checks the real format from its bytes, and afterwards moves it to originals/ so it can be reprocessed later.

  7. 7
    Worker → R2 media

    One WebP master, at most 2000 × 2000, goes to products/<id>/primary/<mediaId>.webp with a one-year immutable cache header.

  8. 8
    Worker → MongoDB

    The row becomes READY with key, width, height, ThumbHash and average colour, and those are copied onto the product so reads need no join.

05

Cloudflare delivery

Cloudflare Image Transformations resize the master when the URL asks for a size. The options live in the path, so changing a size is a string change, not a deploy of new files.

https://images.example.com/cdn-cgi/image/width=540,quality=80,fit=scale-down,format=auto,sharpen=1/products/gb-1g-24k-999/primary/6730f2c19e4b0a1d2c3e4f50.webp

One master, five sizes (to scale)

What happens on a view

A new photo always gets a new mediaId, so it has a new URL. Old sizes simply stop being requested and age out of the cache. Nothing ever needs purging.

App: one helper builds every URL

export const IMAGE_SIZES = { thumb: 160, cardS: 360, card: 540, detail: 1200, zoom: 2000 }

export function imageUrl(key, size, format = 'webp') {
  const w = IMAGE_SIZES[size]
  const opts = [
    `width=${w}`, 'fit=scale-down',
    `quality=${w >= 1200 ? 85 : 80}`,
    `format=${format}`,
    w <= 540 && 'sharpen=1',
  ].filter(Boolean).join(',')
  return `${CDN}/cdn-cgi/image/${opts}/${key}`
}

Web: let the browser pick

  alt="1 g 24 kt 999 gold bar, front"
  loading="lazy" decoding="async">

Width and height from the API reserve the box, so the grid doesn't jump.

Rules for app screens: render product images only through one component that takes a size; prefetch the same sized URL the screen will show (a prefetch of the master is a different cache key and is wasted); use virtualised lists for grids over about six items.

07

CPU, memory and bandwidth

Three places get cheaper: our worker, our origin on every view, and the customer's phone.

Worker CPU per uploaded photo est.

Pre-generating = 5 widths × 3 formats (JPEG, WebP, AVIF) = 15 encodes, with AVIF the slowest at about 6 s of the total. This design = one decode, one resize, one WebP master and the hashes. For 1,500 products × 4 photos that is about 13 CPU-hours vs 1.5. Confirm with the processingTimeMs the worker logs.

Origin CPU on every view

If our servers resized on request, each view would cost about 0.15 s of CPU est.: 1,000,000 views a month ≈ 42 CPU-hours. With the edge, our servers spend 0. Cloudflare makes each size once and serves the rest from cache; R2 is read only on a cache miss.

The customer's phone

Decoding work and memory grow with pixel count (width × height × 4 bytes). A 540 card is 0.29 MP vs 4.0 MP for the master: 93% fewer pixels. A grid of 24 bars needs about 28 MB instead of 384 MB, which is the difference between smooth scrolling and a crash on a budget Android phone.

Placeholders and colour

Every product image arrives with a ThumbHash (about 30 bytes) and its average colour, so a tile paints before any image request finishes.

Why ThumbHash, not BlurHash

BlurHash has no transparency, so a cut-out bar flattens onto white and the placeholder flashes a white square on a purple tile. ThumbHash keeps alpha and the aspect ratio. Keep the placeholder's fit equal to the image's fit, or the blur visibly jumps when the image lands.

Using the average colour

The app can tint the product tile, glow or detail-page background from the average colour, with fixed lightness so text stays readable. For a busy lifestyle shot the average turns muddy, so fall back to the brand tile colour there.

09

Cloudflare setup and cost

Setup checklist

  • Two R2 buckets: uploads (private) and media (public through a custom domain such as images.<domain>).
  • Turn on Image Transformations for that zone, and allow resizing only from our own image domain.
  • CORS on the uploads bucket: PUT with Content-Type from the admin's origin only.
  • Lifecycle rule: delete uploads/ objects after 1 day.
  • Masters carry Cache-Control: public, max-age=31536000, immutable.
  • Optional: a Worker can apply the same options with fetch(url, { cf: { image: { … } } }) if we want short preset URLs later.

EndpointPurpose

Clients receive the key and metadata and build sized URLs with the one helper from section 06, so sizes can change in the apps without an API release.

Rollout plan

Each phase is usable on its own and has a check that tells us it worked.

Phase1Storage
  • Create both R2 buckets, CORS, lifecycle rule, custom image domain.
  • Signed-URL endpoint with type and size signed in.

Done when: an 8 MB bar photo uploads from the admin and API logs show no image bytes.

Phase2Worker
  • Media rows, queue, sharp worker as its own process.
  • sRGB conversion, square check, ThumbHash, average colour.

Done when: 95% of uploads are READY within 5 s, and bad files are FAILED with a reason.

Phase3Delivery
  • Turn on Image Transformations; ship the imageUrl helper and five sizes in app and web.
  • srcset and sizes on every web product image.

Done when: product cards download under 50 KB each and the edge cache hit ratio is over 95% after a day.

Phase4Polish
  • ThumbHash placeholders and tile colours.
  • Prefetch the sized URLs for the home grid.

Done when: no empty tiles in the grid, and web product pages reach p75 LCP under 2.5 s.

Phase5Harden
  • Admin-only queue dashboard, ownership check on signing, reprocess endpoint.
  • Clean-up job for replaced photos; alerts on FAILED rate and transformation budget.

Done when: the queue dashboard needs admin login, signing checks product access, and replaced photos are cleaned up.
